# NexusNet Genesis Build Order Design

Date: 2026-07-05
Status: canon-reconciled foundation ordering design; awaiting user review before implementation plan

## Purpose

NexusNet must be built from inception upward. Later systems such as teacher refresh, model-release radar, distillation, recursive dreaming, mobile federation, runtime research, and autonomous self-improvement remain valid NexusNet plans, but they cannot become the first implementation driver. The build order starts with the smallest canonical organism that can own authority, identity, isolation, evidence, memory, events, governance, replay, and runtime visibility.

This document is an ordering layer over existing canon. It does not replace the source book, addenda, ledgers, or current implementation evidence. It reconciles the next build sequence against:

## Source Authority Rule

The source authority chain for future work is:

1. Complete canon book and raw captured exports for pre-addendum intent.
2. Compact canon where it summarizes book decisions.
3. Post-book canon addendum for locked clarifications and post-book deltas.
4. Assimilation ledger for accepted, candidate, blocked, rejected, side-barred, or superseded additions.
5. Consolidation status and July 2026 cluster rulings for current branch, placeholder, reject, and target-family interpretation.
6. Design specs only when they are source-linked by the addendum, ledger, or later approved review.
7. Current code, tests, GitNexus state, and runtime evidence for implementation status.

Any future concept absent from the book must have an addendum or ledger entry before it is treated as accepted NexusNet state. Any future implementation claim must also have current verification evidence.

## Core Ordering Rule

Layer N can be specified before Layer N-1 is implemented, but Layer N must not be claimed production-real until Layer N-1 has:

- a typed contract,
- source/addendum/ledger references,
- runtime-visible state,
- sanitized evidence artifacts,
- focused tests,
- rollback or containment behavior where mutation is possible,
- a control-panel or release Harness inspection path,
- GitNexus/evidence-gated verification for touched code,
- and a clear status label: planned, candidate, shadow, live-control-plane, live-substrate, blocked, side-barred, rejected, superseded, or production-approved.

Placeholders remain valid planning artifacts when clearly labeled. A placeholder is not a defect. A placeholder becomes a defect only when it is presented as implemented behavior without evidence.

Existing live substrate artifacts are anchors, not blanket proof. A layer may reference prior code-backed substrate work, but each implementation slice must re-check current repo state, current tests, current GitNexus status, and current control-panel/runtime visibility before claiming the layer is live.

## Genesis Layers

### Layer 0: Canon, Addendum, Ledger, And Repository Truth

NexusNet begins with canon and repo truth. Before autonomous behavior, the project needs a machine-readable canon index that establishes source order, branch/worktree truth, accepted terminology, future placeholders, blocked items, and the rule that NexusNet is brain-first and mother-brain-owned.

Build first:

- canon source manifest,
- addendum and assimilation-ledger manifest,
- consolidation status pointer,
- planned/blocked/implemented label contract,
- canon contradiction/sidebar ledger,
- source-ref grammar,
- project-root local state boundary,
- repo-state evidence packet.

This layer blocks any work that would promote chat history, source-reverification entries, roadmap ideas, external research, or preserved placeholders into implemented claims.

### Layer 1: Harness Contract, Agent Identity, And NexusBrain Authority

The first active organism boundary is not a teacher, model, workflow, or external runtime. It is a governed preflight plus the primary NexusBrain authority identity.

Build next:

- non-mutating Harness contract preflight,
- required-artifact and loaded-artifact evidence,
- harness-adherence evidence,
- scoped agent identity evidence,
- allow/block/review-required decision receipt,
- raw-secret and unsafe-scope blockers,
- `NexusBrain` authority identity,
- decision envelope,
- authority receipt,
- allowed and denied action classes,
- parent/child brain reference contract,
- mother-brain approval gate,
- read-only status endpoint,
- release Harness summary of authority state.

Layer 1 does not need advanced reasoning. It needs ownership, traceability, scoped identity, refusal power, and proof that a run loaded and followed its required Harness before it can touch sensitive tools, APIs, MCP servers, workflows, or mutation paths.

### Layer 2: Authority And Isolation Fabric

Authority must have an isolation substrate before the hive expands. This layer applies under every AO, expert, workflow, skill, tool, runtime, model, adapter, companion device, and federation path.

Build next:

- permission envelope,
- policy gate receipt,
- sandbox tier contract,
- capability token or delegated-scope contract,
- supply-chain and artifact trust precheck,
- allow/deny/review-required receipts,
- incident and denial receipts,
- tool and adapter command allowlists,
- no ambient credential rule,
- fail-closed behavior for high-risk paths.

This layer blocks tools, skills, node workflows, runtime adapters, companion sync, model downloads, production mutation, and untrusted graph execution.

### Layer 3: Neural Bus, HiveBlackboard, And Plane Trace

After authority and isolation exist, NexusNet needs a common nervous system. The Neural Bus carries typed events. HiveBlackboard carries shared residual state. Plane traces record substrate flow. This prevents later features from creating private ad hoc state.

Build next:

- typed event envelope,
- append-only in-memory and file-backed event ledger,
- activation id and correlation id rules,
- HiveBlackboard snapshot contract,
- plane trace ledger contract,
- event replay reader,
- event privacy labels,
- event-to-control-panel projection,
- artifact-bound downstream consumption rule.

This layer is the foundation for routing, memory, evals, sandboxing, growth, federation, recursive dreaming, and model-release discovery.

### Layer 4: Neural Substrate Ledger Spine

The canon addendum makes the internal neural substrate first-class. NexusNet must not only say it has a hive neural network; it must emit replayable substrate ledgers that show pathways, signals, attention, gates, loss, storage, checkpoints, runtime decisions, and backend/quantization evidence.

Build or verify next:

- HiveActivation artifact,
- first-class neural pathway map,
- synaptic transmission ledger,
- shadow neuroplastic weight ledger,
- laminar microcircuit ledger,
- neuromodulatory state ledger,
- sensory input and temporal positional ledgers,
- memory engram ledger,
- embedding tensor ledger,
- attention routing ledger,
- sparse expert gate ledger,
- residual normalization and feed-forward expert ledgers,
- latent-loop and KV-cache compression ledgers,
- loss/backpropagation and optimizer-school ledgers,
- computational graph, model genome, tensor runtime kernel, layer block stack, and runtime decision ledgers,
- durable storage and checkpoint coverage ledgers,
- backend/quantization execution ledger.

These ledgers remain evidence first. They may inform shadow routing, eval design, teacher review, dream cycles, runtime research, or future model birth, but they must not mutate active routes, model weights, prompts, runtime binaries, node registries, or production state without later sandbox/eval/teacher/federation/governance/release approval.

### Layer 5: Evidence, Artifact Trust, Rollback, And Checkpoint Spine

NexusNet must record what happened before it improves itself. The evidence spine makes every claim inspectable and every mutation rollback-aware.

Build next:

- content-addressed evidence refs,
- artifact trust registry,
- operation receipt,
- checkpoint snapshot contract,
- rewind/restore proof contract,
- rollback record,
- mutation boundary labels,
- sandbox-safe file apply contract,
- authority effect receipt,
- historical sidebar status for failed, blocked, rejected, retired, or superseded candidates.

This layer blocks active self-repair, safe apply, growth, teacher promotion, runtime mutation, distillation, permanent expert birth, and production release.

### Layer 6: Sensory Input, Provenance, And Privacy Gates

Only after evidence and checkpoint semantics exist should NexusNet ingest external or user-derived signals into the hive. Every signal must be typed before routing or storage.

Build next:

- source identity,
- source kind,
- trust tier,
- privacy class,
- redaction status,
- provenance refs,
- consent status,
- rights/license status,
- source quarantine rules,
- sensory event projection onto the Neural Bus.

This layer blocks memory, model-release radar, assimilation intake, federated learning, and private-data training paths.

### Layer 7: Canon Memory, NexusGraph, And Retrieval Foundation

Memory comes after provenance because memory without source identity becomes contamination. NexusNet needs canon retrieval, graph intelligence, and memory planes before complex experts or AOs can operate reliably.

Build next:

- canon memory index,
- project artifact memory,
- NexusGraph Intelligence Fabric v0,
- graph node/edge/event refs,
- source-grounded retrieval packet,
- contradiction and stale-memory markers,
- MemoryEvolutionPassport,

- memory replay endpoint.

This layer internalizes GitNexus-like capability as a mother-brain-owned pattern across permitted connected state, while preserving GitNexus as the current provider/gate for code intelligence.

### Layer 8: Release Harness, Control Panel, And Visualizer

The Harness and Control Panel are not decorative UI. They are the nervous-system inspection surface. Once authority, isolation, events, substrate ledgers, evidence, provenance, and memory exist, the operator and future agents need visible status.

Build next:

- release Harness status-card contract,
- control-panel foundation cards,
- visualizer foundation overlay,
- authority/isolation/event/evidence/memory/substrate counters,
- degraded vs live labels,
- replay drilldown,
- restart replay proof,
- no-raw-content proof.

This layer blocks credible claims that higher layers are alive.

### Layer 9: O/AO/Expert Contract Registry

Only after the core organism can see and remember itself should the hive grow departments and specialists. O/AO/Expert definitions must be contracts first, implementations second.

Build next:

- Orchestrator contract,
- Assistant Orchestrator contract,
- Expert contract,
- brain-scale hierarchy fields,

- memory scope refs,
- failure visibility refs,

- Cluster 9 roster reconciliation as a contract surface.

This layer blocks expert birth, teacher pairings, model specialization, permanent child retention, and advanced routing.

### Layer 10: Eval, Sandbox, Governance, And Immune System

Before NexusNet can improve itself, it must be able to test and contain itself. Evals and sandboxing are the immune system.

Build next:

- sandbox run envelope,
- deterministic closed-sandbox evidence,
- eval case contract,
- regression suite contract,
- calibrated judge/human/domain-check policy,
- red-team finding receipt,
- promotion gate packet,
- quarantine packet,
- rollback proof,
- governance decision packet.

This layer blocks autonomous updates, safe apply, model training, teacher promotion, runtime mutation, permanent expert birth, tool expansion, and production release.

### Layer 11: Model Attach And Inference Harness

Only after authority, isolation, evidence, memory, and governance exist should external models become live execution tools. Attached models are tools and possible teachers, not the brain.

Build next:

- model/provider attach contract,

- provider capability passport,
- runtime ladder,
- model passport registry,

- context and hardware posture,

This layer blocks advanced teacher use, distillation, local runtime expansion, and birthed-model comparison.

### Layer 12: Recursive Dreaming, Self-Repair, Federation, And Growth Signals

Dreaming and self-improvement need the immune system first. Once eval/sandbox/governance exist, NexusNet can safely dream, replay, propose, repair, and aggregate.

Build next:

- high-temperature Dreamer proposal packet,
- low-temperature Dream Reviewer packet,
- failure/prior-conditioned dream context,
- failure learning packet,
- self-repair proposal,
- governed safe-apply cycle,
- sanitized federated learning packet,
- federated prior ledger,

- growth candidate request.

Dreams produce candidates only. They do not become facts, memory truth, active mutations, production routes, or training material without source/provenance, sandbox, eval, security/privacy, teacher review, rollback, and governance gates.

### Layer 13: Teacher Candidate Universe And Teacher Pairings

Teacher candidates and pairings depend on the ability to ingest sources, inspect rights, run evals, compare outputs, and record evidence.

Build next:

- teacher candidate intake,
- TeacherCapabilityPassport,
- ExpertDomainPassport,
- teacher capability card,
- teacher pairing policy,
- two-plus-teacher requirement for every O, AO, Expert, and core node birth verification,
- high-risk domain gate,
- teacher retirement and archive policy,
- teacher replacement recommendation packet.

Leanstral belongs here as a formal-methods and Lean 4 theorem-proving teacher candidate: proof repair, formal specification, theorem decomposition, proof-driven code contracts, and mathematical rigor for expert/AO training. DeepSeek, Qwen, Kimi, Mistral, Devstral, Nemotron, LFM, MiniCPM, medical, finance, crypto, quantum, memory, graph, holistic medicine, law, cybersecurity, and other candidates require the same current-source, license, rights, benchmark, and domain gates. No fixed roster is final.

### Layer 14: Model Release Radar And Downtime Auto-Benchmark

The model-release radar is a later layer. It becomes useful after NexusNet can safely discover, ingest, evaluate, quarantine, ledger, and recommend candidates.

Build after Layer 13:

- model release observation,
- release source adapter,
- downtime scheduler,
- benchmark evidence packet,
- source/license/provenance blocker refs,
- teacher-role recommendation packet,

- control-panel radar status.

Auto-run discovery and benchmark work is allowed during downtime. Auto-promotion remains blocked by the proper pipeline.

### Layer 15: Hive Model Growth Engine And Birthed Model Pipeline

The model NexusNet births requires nearly every prior layer. Growth turns evidence into training material, teacher labels, student birth records, eval gauntlets, shadow artifacts, promotion decisions, and rollback proofs.

Build after teacher/eval/governance foundations:

### Layer 16: Mobile, Edge, Companion, And Hive Federation

Mobile and edge should arrive after the core organism and birthed-model lineage are coherent enough to federate safely. The companion app extends the hive, but it must not become a separate uncontrolled brain.

Build late:

- federated sync packet,

This layer inherits all prior evidence, authority, memory, substrate, and governance rules.

## What Must Be Built First

The first implementation plan after this spec should target Layer 0 through the smallest useful part of Layer 3, while checking existing substrate anchors instead of rewriting them blindly:

1. Canon source manifest.
2. Addendum and assimilation-ledger manifest.
3. Genesis status endpoint or artifact that reports current canon/build-layer state.
4. Harness contract and agent identity preflight in non-mutating mode.
5. Minimal NexusBrain authority envelope.
6. Minimal authority receipt.
7. Minimal permission/isolation receipt.
8. Minimal Neural Bus event envelope and HiveBlackboard snapshot projection.
9. Runtime-visible release Harness/control-panel projection of those foundation signals.
10. Focused tests proving restart-safe, sanitized foundation evidence.

This is intentionally smaller than the full roadmap. It creates the root that later slices can build on.

## Testing Strategy

Every build-order layer should get tests that prove:

- its contract exists,
- it emits sanitized evidence,
- it replays after restart when persistence is expected,
- it refuses to claim dependent higher-layer behavior,
- it exposes degraded or placeholder state honestly,
- it does not leak raw prompt, output, private file, local path, session id, token, credential, or secret data,
- it preserves rollback/containment when mutation is possible,
- it distinguishes candidate, shadow, live-control-plane, live-substrate, and production-approved states,
- it reports control-panel or release Harness evidence.

The first implementation slice should include a red-green test for the Genesis layer status, Harness preflight, NexusBrain authority envelope, permission/isolation receipt, and Neural Bus/HiveBlackboard projection before writing production code.

## Review Rule For Future Specs

Future specs can describe later layers, but each must list:

- earliest build layer,
- prerequisite layers,
- current repo anchors,
- source/addendum/ledger refs,
- blocked claims,
- minimum evidence required before implementation is considered real,
- control-panel/release Harness visibility requirement,
- rollback/sidebar rule,
- and whether the item is a pattern, adapter candidate, teacher candidate, eval candidate, research-only item, blocked direct dependency, locked clarification, live-control-plane surface, live-substrate surface, or production-approved behavior.

This keeps future assimilation work aligned without suppressing placeholders or long-range planning.
